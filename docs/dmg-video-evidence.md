# DMG video evidence ledger

This ledger separates software-authored composition checks from source-derived timing expectations. It does not claim physical DMG observation.

## Source snapshot and applicability

The reference snapshot is the `gbdev/pandocs` repository at commit [`0191af06ac49661587dcde3d57a241a626b8df75`](https://github.com/gbdev/pandocs/commit/0191af06ac49661587dcde3d57a241a626b8df75), retrieved 2026-10-07. These are maintained technical documentation for Game Boy behavior, including DMG; they do not provide a CPU-B-specific hardware observation for every rule. Applicability below is therefore a documented DMG expectation applied to the bootless `GBB_PROFILE_DMG_CPU_B` model, not a physical CPU-B qualification.

For the startup, restart, and FF46 register cases below, source assertions were checked against the immutable Mooneye Test Suite revision [`31510e12eea6286d36eea060a6adde755e1067aa`](https://github.com/Gekkio/mooneye-test-suite/tree/31510e12eea6286d36eea060a6adde755e1067aa). `acceptance/oam_dma_start.s` reports the fresh/restarted M=0/M=1/M=2 OAM-access observations and result tuple B=`$D7`, C=`$01`, D=`$D7`, E=`$00`; `acceptance/oam_dma_restart.s` asserts C=`$FF` one M-cycle before completion and D=`$01` immediately after a replacement transfer; `acceptance/oam_dma/reg_read.s` checks `$9F`, `$42`, `$8F`, and `$3F`. Their pass tables report DMG-family success, and the suite README lists a DMG-CPU-B unit in its manually tested fleet. It does not retain per-test/per-unit raw logs, so this is upstream author-supplied hardware-test evidence plus our owned software regression, not a project physical observation.

For JOYP, primary DMG-family documentation is Nintendo's [*Game Boy Programming Manual* v1.1](https://archive.org/details/GameBoyProgManVer1.1/page/n23/mode/2up). CPU-B circuit references are the `msinger/dmg-schematics` source files pinned to commit [`28f66aedf974b91aafeb42443f2b731fcd7769e7`](https://github.com/msinger/dmg-schematics/commit/28f66aedf974b91aafeb42443f2b731fcd7769e7): [FF00 JOYP](https://github.com/msinger/dmg-schematics/blob/28f66aedf974b91aafeb42443f2b731fcd7769e7/dmg_cpu_b/ff00_joyp.kicad_sch), [clock/reset](https://github.com/msinger/dmg-schematics/blob/28f66aedf974b91aafeb42443f2b731fcd7769e7/dmg_cpu_b/clocks_and_reset.kicad_sch), and [FF0F interrupt](https://github.com/msinger/dmg-schematics/blob/28f66aedf974b91aafeb42443f2b731fcd7769e7/dmg_cpu_b/ff0f_int.kicad_sch). The repository describes these as reverse-engineered schematics derived from Furrtek's work and warns that reconstructed logic may contain errors; they are circuit-inference evidence, not Nintendo documentation or a physical observation. No schematic image or source file is copied into this repository.

## DMA and access evidence matrix

The mirror-hosted scan of Nintendo's *Game Boy Programming Manual*, Chapter 2 §1.8.1, pp. 60–61, says DMG OAM DMA copies 160 bytes, takes 160 μs, accepts aligned source pages in `$8000–$DFFF`, and cannot source from ROM `$0000–$7FFF`; its examples cover WRAM and display RAM. This conflicts with the pinned Pan Docs [OAM DMA Transfer section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/OAM_DMA_Transfer.md), which allows pages `$00–$DF` and describes ROM/RAM sources. This implementation follows the manual's narrower DMG source range. The supported ROM-only profile has no external cartridge RAM, so `$A000–$BFFF` reads as `$FF` under current mapper scope. The manual says the CPU routine runs from HRAM to avoid bus conflicts; Pan Docs further states that DMG CPU access is restricted to HRAM during DMA. Those documents do not specify active-transfer FF46 restart or register-read behavior; the pinned Mooneye acceptance cases cited above supply those upstream DMG-family assertions. No test treats them as a project physical CPU-B observation.

| Case | Asserted behavior | Evidence and qualification |
|---|---|---|
| `dma_progress` | An HRAM guest starts a 160-byte transfer. The observer records bytes at one-M-cycle intervals, with the first byte at start+8 half-dots and the final byte/completion at start+1280. Guest reads immediately before and after completion see blocked then available WRAM. | Manual §1.8.1 supports transfer size and duration; Pan Docs supports 160 M-cycles. The per-byte cadence and first-byte offset are the selected timeline interpretation. The CPU reads occur at +1272 and +1288; the implementation processes the final DMA byte before a CPU access at the same timestamp, but no 2-M-cycle guest read can land exactly at +1280. This ordering is deterministic emulator policy, not a measured bus tie-break. |
| `dma_source_mapping` | Pages `$80`, `$9F`, `$C0`, and `$DF` map to VRAM/WRAM and copy the first/last legal-page data without crossing bounds. ROM, external RAM without a cartridge RAM implementation, echo, and unusable pages produce `$FF` in this model. | The chosen DMG source envelope follows the manual. ROM-source support is a documented source conflict; the test records the selected policy and does not claim agreement across revisions. |
| `dma_hram` | HRAM instruction fetches and HRAM reads/writes continue. Non-HRAM guest reads return `$FF` and writes are ignored during DMA for WRAM, VRAM, and OAM; DMA still reads its VRAM/WRAM source and writes OAM. Post-transfer guest reads confirm the source byte and copied OAM byte. | HRAM execution and avoiding external bus conflicts are documented. `$FF` and ignored-write results are explicit model behavior; exact CPU-B electrical values are not qualified. |
| `dma_start` | An original guest initializes OAM with `INC B`, starts page `$80` DMA by executing a bus write from the OAM echo predecessor, and observes B=`$01` after the first OAM instruction. The observer then checks the `$D7` source byte at start+8 half-dots and the complete 160-byte copy. | Corresponds to the fresh-transfer M=0/M=1/M=2 case in pinned `acceptance/oam_dma_start.s`; the owned test confirms the first-cycle OAM instruction is available before ordinary active-transfer gating. The upstream source additionally supplies result tuple B=`$D7`, C=`$01`, D=`$D7`, E=`$00`; the owned guest does not claim to recreate all four final registers. The PPU is disabled, so no scan/fetch arbitration is asserted. |
| `dma_restart` | An original HRAM guest writes FF46 again while the first transfer is active. The PPU is disabled for this timing guest, so the assertion does not involve simultaneous PPU/DMA arbitration. The upstream source reports DMG-family pass, with no per-unit retained log. |
| `dma_register_readback` | HRAM guests read `$9F` after start, `$42` after an active restart, `$8F` and `$3F` after two active writes, and `$8F`/`$3F` after completed transfers. | Corresponds to the exact values in pinned `acceptance/oam_dma/reg_read.s`. The guest program is original and checks FF46 values through CPU bus operations. `$3F` is a register-only probe outside D-024's source range; it does not widen the modeled DMA source mapping. |
| `dma_partition` | One run and adjacent budget partitions produce identical DMA events and completed shade frames. | Metamorphic software property only; it is not independent hardware evidence. |
| `dma_vram_lock`, `dma_oam_lock` | Guest reads/writes verify LCD-off and mode 0/1 access; reads straddle the mode 2→3 and mode 3→0 ownership changes at recorded bus timestamps; reads return `$FF` while locked, and writes during each lock preserve the prior value. | DMG mode access expectations follow the pinned Accessing VRAM and OAM section. The closest mode 2→3 guest reads are 8 half-dots on either side; mode 3→0 reads also straddle the transition. No CPU-B board was available for direct observation. |
| `dma_contention` | Bounded work confirms per-instance DMA state is isolated and reset stops an in-flight transfer without later byte events. | OAM scan/render collisions during DMA are revision-dependent in the source and deliberately have no pass/fail outcome here. The test does not treat reset/isolation as proof of collision behavior; exact CPU-B primary evidence remains unavailable. |

### Simultaneous PPU/DMA applicability

No new collision assertion is added because the available sources do not provide an exact DMG-CPU-B expected outcome for these cases. The existing focused `dma_*` and `ppu_timing_*` families remain registered in both `tests/CMakeLists.txt` and `tests/expected-tests.txt`; `dma_contention` tests reset/isolation, not a CPU/PPU/DMA collision.

| Collision scenario | Pinned-source statement | Applicability and test disposition |
|---|---|---|
| DMA overlaps PPU mode 2 OAM scan | Pan Docs says most PPU revisions read objects as off-screen while DMA is active. | “Most revisions” does not identify DMG-CPU-B. No object-visibility pass/fail expectation is asserted. |
| DMA overlaps PPU mode 3 object fetch | Pan Docs describes the PPU reading the 16-bit word currently written by DMA, with revision-dependent effects. | The source does not qualify the result to this CPU-B path. No tile/attribute corruption expectation is asserted. |
| CPU, PPU, and DMA contend at one timestamp | The available manual and pinned Pan Docs do not define a CPU-B tie-break for the exact simultaneous access used by this core. | The implementation's ordering remains policy. No test promotes it to hardware behavior. |

The test programs are original guest-authored bytes. No upstream ROM, package, or new fixture dependency was admitted. The pinned suite's broad DMG-family result and documented fleet do not establish a retained project observation on a specific CPU-B unit. D-024's `$8000–$DFFF` ROM-only source policy and its conflict with `sources-GS.s` remain unchanged. External cartridge RAM mapping, blocked-bus electrical values, coincident CPU/DMA/PPU ownership, and revision-specific OAM corruption remain open evidence gaps rather than qualified behaviors.

## Joypad matrix and interrupt evidence

The pinned [Pan Docs Joypad Input section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Joypad_Input.md) describes the active-low P14/P15 matrix and selected-row reads, but not the exact JOYP interrupt sampling sequence. Nintendo's *Game Boy Programming Manual* v1.1, Chapter 1 §2.4.1, printed p. 24, documents the direction/action row mapping, two reads after selecting P14, six reads after selecting P15, and a negative-edge P10–P13 input interrupt requiring a low period of (2^4) source-oscillator periods—16 periods, not 24 (DMG source oscillation is listed as 4 MHz). The printed exponent matters: text extraction can flatten (2^4) to `24`. This is primary DMG-family documentation, but it does not give a CPU-B sample phase or an exact JOYP-write-to-IF timestamp. The [2017 hardware research note](https://gekkio.fi/blog/2017/game-boy-research-status/) reports synchronous samples where two low observations can request the interrupt even with a high interval between them; its exact clock count and CPU revision were not established, so it remains context rather than an expected-value oracle.

## Timing expectation matrix

Timing cases use guest bus observations and the private test observer; each row records dots from the start of a visible scanline, where one dot is two core half-dots. CPU bus operations occur at their scheduled machine phases, so the test asserts the observed access timestamp and register value rather than treating a rendered image as a timing oracle.

| Case | Primary documented expectation | Applicability / unverified boundary |
|---|---|---|
| `ppu_timing_modes` baseline | LCD is disabled, mode sources are clear, then the guest enables LCDC. Relative to the FF40 enable write: mode 2 starts at +0 half-dots; mode 3 at +160; mode 0 at +504; next-line mode 2 at +912. Guest STAT reads at +496, +504 and +512 distinguish the HBlank boundary. | Pan Docs Rendering: 80-dot mode 2, baseline 172-dot mode 3, 456 dots/line. CPU-B read phase not physically observed. |
| `ppu_timing_fetch` SCX=3 | Guest writes SCX=3 while LCD is off, enables LCDC=$91, executes 60 NOPs, then reads STAT at enable+504 half-dots (dot 252). This focused case distinguishes the current fixed cutoff. |
| Fetch matrix: window | With SCX=0, LCDC window enabled, WY=0/WX=7, expect mode 0 at dot 258 (+516 half-dots). WX=0 and SCX=3 combines the documented one-dot shortening with the normal six-dot restart: dot 260 (+520 half-dots). | Pan Docs Pixel FIFO / Rendering. The implementation uses fixed per-instance storage: a 16-slot transfer queue, four two-dot fetch stages, at most ten selected objects, and fixed frame buffers. Queue entries identify bounded output-pixel slots; the common compositor resolves tile and object shade at emission. This supplies deterministic output pacing and bounded work, but it does not claim cycle-level equivalence of internal DMG FIFO contents or CPU-B fetch circuitry. The test-only PPU observer records mode changes, combined STAT rising edges, LY changes, and VBlank entry; public production APIs remain unchanged.

No case in this plan substitutes agreement with another emulator for hardware evidence. Any unlisted revision-sensitive effect is outside the claim and remains an evidence gap.
