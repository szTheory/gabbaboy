# DMG video evidence ledger

This ledger separates software-authored composition checks from source-derived timing expectations. It does not claim physical DMG observation.

## Source snapshot and applicability

The reference snapshot is the `gbdev/pandocs` repository at commit [`0191af06ac49661587dcde3d57a241a626b8df75`](https://github.com/gbdev/pandocs/commit/0191af06ac49661587dcde3d57a241a626b8df75), retrieved 2026-10-07. For the startup, restart, and FF46 register cases below, source assertions were checked against the immutable Mooneye Test Suite revision [`31510e12eea6286d36eea060a6adde755e1067aa`](https://github.com/Gekkio/mooneye-test-suite/tree/31510e12eea6286d36eea060a6adde755e1067aa). `acceptance/oam_dma_start.s` reports the fresh/restarted M=0/M=1/M=2 OAM-access observations and result tuple B=`$D7`, C=`$01`, D=`$D7`, E=`$00`; `acceptance/oam_dma_restart.s` asserts C=`$FF` one M-cycle before completion and D=`$01` immediately after a replacement transfer; `acceptance/oam_dma/reg_read.s` checks `$9F`, `$42`, `$8F`, and `$3F`. ## DMA and access evidence matrix

The mirror-hosted scan of Nintendo's *Game Boy Programming Manual*, Chapter 2 §1.8.1, pp. 60–61, says DMG OAM DMA copies 160 bytes, takes 160 μs, accepts aligned source pages in `$8000–$DFFF`, and cannot source from ROM `$0000–$7FFF`; its examples cover WRAM and display RAM. This conflicts with the pinned Pan Docs [OAM DMA Transfer section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/OAM_DMA_Transfer.md), which allows pages `$00–$DF` and describes ROM/RAM sources. This implementation follows the manual's narrower DMG source range. The supported ROM-only profile has no external cartridge RAM, so `$A000–$BFFF` reads as `$FF` under current mapper scope. The manual says the CPU routine runs from HRAM to avoid bus conflicts; Pan Docs further states that DMG CPU access is restricted to HRAM during DMA. Those documents do not specify active-transfer FF46 restart or register-read behavior; the pinned Mooneye acceptance cases cited above supply those upstream DMG-family assertions. No test treats them as a project physical CPU-B observation.

| Case | Asserted behavior | Evidence and qualification |
|---|---|---|
| `dma_progress` | An HRAM guest starts a 160-byte transfer. The observer records bytes at one-M-cycle intervals, with the first byte at start+8 half-dots and the final byte/completion at start+1280. Guest reads immediately before and after completion see blocked then available WRAM. | Manual §1.8.1 supports transfer size and duration; Pan Docs supports 160 M-cycles. The per-byte cadence and first-byte offset are the selected timeline interpretation. The CPU reads occur at +1272 and +1288; the implementation processes the final DMA byte before a CPU access at the same timestamp, but no 2-M-cycle guest read can land exactly at +1280. This ordering is deterministic emulator policy, not a measured bus tie-break. |

ROM-source support is a documented source conflict; the test records the selected policy and does not claim agreement across revisions. |
| `dma_hram` | HRAM instruction fetches and HRAM reads/writes continue. | `dma_vram_lock`, `dma_oam_lock` | Guest reads/writes verify LCD-off and mode 0/1 access; reads straddle the mode 2→3 and mode 3→0 ownership changes at recorded bus timestamps; reads return `$FF` while locked, and writes during each lock preserve the prior value. | DMG mode access expectations follow the pinned Accessing VRAM and OAM section. The closest mode 2→3 guest reads are 8 half-dots on either side; mode 3→0 reads also straddle the transition. No CPU-B board was available for direct observation. |

| `dma_ppu_overlap` | Original guests assert no-DMA pixels, mode-2 partial overlap (an entry sampled before DMA stays visible while a later entry is suppressed), and DMA completed before scanning. ### Simultaneous PPU/DMA applicability

The owner-authorized model policy uses published documentation and established emulator implementations to choose testable behavior where exact CPU-B phase results are unavailable. Original guests exercise no-DMA, partial mode-2 overlap, completion-before-scan, mode-3 fetch-word boundaries, active-DMA CPU access in all PPU modes, and an exact three-way collision. Pixels, DMA bytes, CPU bus results and timestamps are independently asserted. These outcomes are software-model behavior, not physical CPU-B qualification.

| Collision scenario | Pinned-source statement | Applicability and test disposition |
|---|---|---|
| DMA overlaps PPU mode 2 OAM scan | Pan Docs says most PPU revisions read objects as off-screen while DMA is active. | `dma_ppu_overlap` asserts per-entry suppression, a pre-sampled object control, a completed-before-scan control, and partition equivalence. “Most revisions” does not identify CPU-B; exact scan phase remains unmeasured. |
| DMA overlaps PPU mode 3 object fetch | Pan Docs describes a fetch of the 16-bit word currently written by DMA, with revision-dependent effects; SameBoy, mGBA, and Gambatte implement differing or explicitly unresolved DMA visibility behavior. | `dma_ppu_word_boundaries` checks fetches immediately before/after byte updates; `dma_ppu_cpu_collision` checks the same-dot DMA-first tie. Aligned word choice and tie are explicit repository policy; CPU-B applicability remains unmeasured. |
| CPU, PPU, and DMA contend at one timestamp | The available manual and pinned Pan Docs do not define a CPU-B tie-break for this exact coincidence. | `dma_ppu_cpu_collision` registers a guest-level coincidence and separately asserts the DMA byte, PPU-latched shade, and blocked CPU result. Partitioned execution preserves them. This closes the software-model coverage gap without claiming hardware qualification. |

The test programs are original guest-authored bytes. No upstream ROM, package, or new fixture dependency was admitted. The pinned suite's broad DMG-family result and documented fleet do not establish a retained project observation on a specific CPU-B unit. D-024's `$8000–$DFFF` ROM-only source policy and its conflict with `sources-GS.s` remain unchanged. External cartridge RAM mapping, blocked-bus electrical values, coincident CPU/DMA/PPU ownership, and revision-specific OAM corruption remain open evidence gaps rather than qualified behaviors.

An independent DMG-CPU-B gate/cell-level model was also reviewed at pinned [`msinger/dmg-sim`](https://github.com/msinger/dmg-sim/tree/786f8c8aaac7ae507eac2a59f2a7d3d5e91dfe66), generated from [reverse-engineered CPU-B schematics](https://github.com/msinger/dmg-schematics/tree/28f66aedf974b91aafeb42443f2b731fcd7769e7). Its published test table includes an MGB-specific OAM-DMA/HALT sprite case, not an exact CPU-B oracle for our scan/fetch or coincident bus cases; its test table has no joypad input-to-IF case. The original test author reports model and individual-unit variation in real collision data. Under Plan 03-04's evidence rule, this other emulator model is a research lead, not a substitute for an applicable primary result or identified CPU-B observation. No dependency or third-party fixture is added.

## Joypad matrix and interrupt evidence

The pinned [Pan Docs Joypad Input section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Joypad_Input.md) describes the active-low P14/P15 matrix and selected-row reads, but not the exact JOYP interrupt sampling sequence. Nintendo's *Game Boy Programming Manual* v1.1, Chapter 1 §2.4.1, printed p. 24, documents the direction/action row mapping, two reads after selecting P14, six reads after selecting P15, and a negative-edge P10–P13 input interrupt requiring a low period of (2^4) source-oscillator periods—16 periods, not 24 (DMG source oscillation is listed as 4 MHz). The printed exponent matters: text extraction can flatten (2^4) to `24`. This is primary DMG-family documentation, but it does not give a CPU-B sample phase or an exact JOYP-write-to-IF timestamp. The [2017 hardware research note](https://gekkio.fi/blog/2017/game-boy-research-status/) reports synchronous samples where two low observations can request the interrupt even with a high interval between them; its exact clock count and CPU revision were not established, so it remains context rather than an expected-value oracle.

## Timing expectation matrix

CPU bus operations occur at their scheduled machine phases, so the test asserts the observed access timestamp and register value rather than treating a rendered image as a timing oracle.

|---|---|---|

The implementation uses fixed per-instance storage: a 16-slot transfer queue, four two-dot fetch stages, at most ten selected objects, and fixed frame buffers. Queue entries identify bounded output-pixel slots; the common compositor resolves tile and object shade at emission. This supplies deterministic output pacing and bounded work, but it does not claim cycle-level equivalence of internal DMG FIFO contents or CPU-B fetch circuitry. The test-only PPU observer records mode changes, combined STAT rising edges, LY changes, and VBlank entry; public production APIs remain unchanged.

No case in this plan substitutes agreement with another emulator for hardware evidence. Any unlisted revision-sensitive effect is outside the claim and remains an evidence gap.
