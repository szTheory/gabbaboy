# DMG video evidence ledger

This ledger separates software-authored composition checks from source-derived timing expectations. It does not claim physical DMG observation.

## Source snapshot and applicability

The reference snapshot is the `gbdev/pandocs` repository at commit [`0191af06ac49661587dcde3d57a241a626b8df75`](https://github.com/gbdev/pandocs/commit/0191af06ac49661587dcde3d57a241a626b8df75), retrieved 2026-10-07. Relevant source sections are [Rendering](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Rendering.md), [Pixel FIFO](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/pixel_fifo.md), [Tile Maps](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Tile_Maps.md), [Tile Data](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Tile_Data.md), [Graphics](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Graphics.md), [Accessing VRAM and OAM](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Accessing_VRAM_and_OAM.md), and [Interrupt Sources](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Interrupt_Sources.md). These are maintained technical documentation for Game Boy behavior, including DMG; they do not provide a CPU-B-specific hardware observation for every rule. Applicability below is therefore a documented DMG expectation applied to the bootless `GBB_PROFILE_DMG_CPU_B` model, not a physical CPU-B qualification.

## DMA and access evidence matrix

The mirror-hosted scan of Nintendo's *Game Boy Programming Manual*, Chapter 2 §1.8.1, pp. 60–61, says DMG OAM DMA copies 160 bytes, takes 160 μs, accepts aligned source pages in `$8000–$DFFF`, and cannot source from ROM `$0000–$7FFF`; its examples cover WRAM and display RAM. This conflicts with the pinned Pan Docs [OAM DMA Transfer section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/OAM_DMA_Transfer.md), which allows pages `$00–$DF` and describes ROM/RAM sources. This implementation follows the manual's narrower DMG source range. The supported ROM-only profile has no external cartridge RAM, so `$A000–$BFFF` reads as `$FF` under current mapper scope. The manual says the CPU routine runs from HRAM to avoid bus conflicts; Pan Docs further states that DMG CPU access is restricted to HRAM during DMA. Neither source supplies a CPU-B observation of blocked-read values, write effects, active-transfer FF46 restart behavior, or the exact first-byte phase. No test treats those missing details as physical CPU-B evidence.

| Case | Asserted behavior | Evidence and qualification |
|---|---|---|
| `dma_progress` | An HRAM guest starts a 160-byte transfer. The observer records bytes at one-M-cycle intervals, with the first byte at start+8 half-dots and the final byte/completion at start+1280. Guest reads immediately before and after completion see blocked then available WRAM. | Manual §1.8.1 supports transfer size and duration; Pan Docs supports 160 M-cycles. The per-byte cadence and first-byte offset are the selected timeline interpretation. The CPU reads occur at +1272 and +1288; the implementation processes the final DMA byte before a CPU access at the same timestamp, but no 2-M-cycle guest read can land exactly at +1280. This ordering is deterministic emulator policy, not a measured bus tie-break. |
| `dma_source_mapping` | Pages `$80`, `$9F`, `$C0`, and `$DF` map to VRAM/WRAM and copy the first/last legal-page data without crossing bounds. ROM, external RAM without a cartridge RAM implementation, echo, and unusable pages produce `$FF` in this model. | The chosen DMG source envelope follows the manual. ROM-source support is a documented source conflict; the test records the selected policy and does not claim agreement across revisions. |
| `dma_hram` | HRAM instruction fetches and HRAM reads/writes continue. Non-HRAM guest reads return `$FF` and writes are ignored during DMA for WRAM, VRAM, and OAM; DMA still reads its VRAM/WRAM source and writes OAM. Post-transfer guest reads confirm the source byte and copied OAM byte. | HRAM execution and avoiding external bus conflicts are documented. `$FF` and ignored-write results are explicit model behavior; exact CPU-B electrical values are not qualified. |
| `dma_restart` | A guest attempts to write FF46 again while DMA is active; because FF46 lies outside HRAM, the CPU bus gate ignores the write and the first transfer completes. | This checks the model's HRAM-only access rule. Neither source specifies accepted restart semantics, so it is not a hardware-qualified restart test and remains an evidence gap. |
| `dma_partition` | One run and adjacent budget partitions produce identical DMA events and completed shade frames. | Metamorphic software property only; it is not independent hardware evidence. |
| `dma_vram_lock`, `dma_oam_lock` | Guest reads/writes verify LCD-off and mode 0/1 access; reads straddle the mode 2→3 and mode 3→0 ownership changes at recorded bus timestamps; reads return `$FF` while locked, and writes during each lock preserve the prior value. | DMG mode access expectations follow the pinned Accessing VRAM and OAM section. The closest mode 2→3 guest reads are 8 half-dots on either side; mode 3→0 reads also straddle the transition. No CPU-B board was available for direct observation. |
| `dma_contention` | Bounded work confirms per-instance DMA state is isolated and reset stops an in-flight transfer without later byte events. | OAM scan/render collisions during DMA are revision-dependent in the source and deliberately have no pass/fail outcome here. The test does not treat reset/isolation as proof of collision behavior; exact CPU-B primary evidence remains unavailable. |

The test programs are original guest-authored bytes. No upstream ROM, package, or new fixture dependency was admitted. Restart acceptance, external cartridge RAM mapping, blocked-bus electrical values, coincident CPU/DMA/PPU ownership, and revision-specific OAM corruption remain open evidence gaps rather than qualified behaviors.

## Joypad matrix and interrupt evidence

The pinned [Pan Docs Joypad Input section](https://github.com/gbdev/pandocs/blob/0191af06ac49661587dcde3d57a241a626b8df75/src/Joypad_Input.md) describes the active-low P14/P15 matrix and selected-row reads, but not the exact JOYP interrupt sampling sequence. Nintendo's [*Game Boy Programming Manual* v1.1](https://archive.org/download/GameBoyProgManVer1.1/GameBoyProgManVer1.1.pdf), Chapter 1 §2.4.1 and §2.4.4, pp. 24–26, documents the direction/action row mapping, two reads after selecting P14, six reads after selecting P15, and a negative-edge input interrupt that requires a low period of 24 source-oscillator periods (DMG: 4 MHz). This is primary DMG-family documentation, but it does not pin the pulse-sampling phase or row-switch/held-key interaction to DMG-CPU-B. The [2017 hardware research note](https://gekkio.fi/blog/2017/game-boy-research-status/) reports synchronous samples where two low observations can request the interrupt even with a high interval between them; the exact clock count and CPU revision were not established there. The manual's continuous-low threshold does not resolve that observed sampling sequence.

A DMG-CPU-B-specific [die-derived schematic set](https://github.com/msinger/dmg-schematics/tree/786f8c8aaac7ae507eac2a59f2a7d3d5e91dfe66/dmg_cpu_b) includes the [FF00 joypad](https://github.com/msinger/dmg-schematics/blob/786f8c8aaac7ae507eac2a59f2a7d3d5e91dfe66/dmg_cpu_b/ff00_joyp.kicad_sch) and [FF0F interrupt](https://github.com/msinger/dmg-schematics/blob/786f8c8aaac7ae507eac2a59f2a7d3d5e91dfe66/dmg_cpu_b/ff0f_int.kicad_sch) sheets. It shows clocked input sampling and an `INT_JP` path, making it a useful CPU-B-specific research source, but the reconstructed schematic has not been traced end-to-end into independently expected half-dot cases for press, release, held-key row switching, and just-before/at/after sample edges. The manual, hardware note, and die-derived circuit therefore do not yet close D-08 as an executable CPU-B behavior contract. No JOYP interrupt edge is implemented or asserted; VIDEO-03 remains incomplete.

| Case | Asserted behavior | Evidence and qualification |
|---|---|---|
| `joypad_selection` | Guest writes each P14/P15 selection, performs two P14 reads or six P15 reads, then checks active-low results for each button, both rows, neither row, and all buttons together. Two instances retain independent button state. | Nintendo Programming Manual §2.4.1 and pinned Pan Docs establish matrix selection/read semantics and settling guidance. This is a guest-visible model test, not a physical CPU-B observation. |
| `joypad_queue_atomic` | Invalid batches append nothing; past timestamps and capacity overflow are rejected; a full 64-event queue is accepted, a further event is rejected, and reset clears pending/held input. | Public API contract and direct finite guest reads. No IRQ result is inferred from these queue checks. |
| `joypad_equal_time` | Press/release events at one timestamp retain caller order and produce the corresponding polled state. | Deterministic queue contract; software behavior only. |
| `joypad_partition` | Whole and adjacent-partition runs consume the same press/release timestamps and produce identical guest-visible samples. | Metamorphic determinism check; it does not qualify hardware sampling or interrupt timing. |
| JOYP interrupt selection/transition | No IF assertion is made for selection writes, held keys, or press/release transitions. | D-08 remains open: Nintendo documents a 24-source-cycle low threshold, while the hardware note reports a synchronous multi-sample effect and the DMG-CPU-B die-derived circuit has not been traced to exact expected timestamps. VIDEO-03 is therefore not complete. |

The original guest-authored polling tests consume only the public event queue and FF00 register path. SDL behavior, emulator agreement, and the visible-demo fixture are not used as interrupt evidence.

## Timing expectation matrix

Timing cases use guest bus observations and the private test observer; each row records dots from the start of a visible scanline, where one dot is two core half-dots. CPU bus operations occur at their scheduled machine phases, so the test asserts the observed access timestamp and register value rather than treating a rendered image as a timing oracle.

| Case | Primary documented expectation | Applicability / unverified boundary |
|---|---|---|
| `ppu_timing_modes` baseline | LCD is disabled, mode sources are clear, then the guest enables LCDC. Relative to the FF40 enable write: mode 2 starts at +0 half-dots; mode 3 at +160; mode 0 at +504; next-line mode 2 at +912. Guest STAT reads at +496, +504 and +512 distinguish the HBlank boundary. | Pan Docs Rendering: 80-dot mode 2, baseline 172-dot mode 3, 456 dots/line. CPU-B read phase not physically observed. |
| `ppu_timing_fetch` SCX=3 | Guest writes SCX=3 while LCD is off, enables LCDC=$91, executes 60 NOPs, then reads STAT at enable+504 half-dots (dot 252). Expected mode is still 3; source-derived HBlank begins at dot 255 / enable+510 half-dots. The bus observer records the guest read timestamp. | Pan Docs Rendering: `SCX % 8` extra dots. This focused case distinguishes the current fixed cutoff. |
| Fetch matrix: window | With SCX=0, LCDC window enabled, WY=0/WX=7, expect mode 0 at dot 258 (+516 half-dots). WX=0 and SCX=3 combines the documented one-dot shortening with the normal six-dot restart: dot 260 (+520 half-dots). | Pan Docs Pixel FIFO / Rendering. Window activation/restart write edges and revision quirks are not generalized here. |
| Fetch matrix: objects | With SCX=0, LCDC objects enabled, OAM Y=16/X=8, the first visible OBJ pixel has five fetch-wait dots plus the flat six-dot fetch penalty: mode 0 at dot 263 (+526 half-dots). X=14 starts at screen x=6 in the same BG tile and adds the flat six: dot 258 (+516). A second object at X=12 in that tile adds six more: dot 269 (+538). | Pan Docs Rendering OBJ penalty algorithm. No DMA overlap or mid-line OAM mutation claim. X=0 with nonzero SCX and negative/offscreen sprite starts are excluded because penalty ordering is unconfirmed. |
| VBlank / wrap | LY=144 begins at enable+144×912 half-dots, enters mode 1, and requests IF bit 0; LY wraps after 154×912 half-dots. A finite guest polls IF and LY through the CPU-visible registers. | Pan Docs Interrupt Sources / Rendering. Emulator bootless startup and LCD toggle phase remain explicit policy, not measured hardware. |
| `ppu_timing_stat` | Enable Mode 0 and Mode 2 STAT sources before LCD; assert edges at enable/Mode 2 and first HBlank, no new edge at next line's Mode 2 while the ORed line remains high; then a new HBlank edge after Mode 3 lowers it. A separate LYC=1-only case asserts the coincidence edge at line 1. | Pan Docs Interrupt Sources: ORed source line, rising-edge request. STAT-write transient and sub-dot LYC quirk excluded. |
| `ppu_timing_lcd` | Guest reads LCDC/STAT/SCY/SCX/LY/LYC/BGP/OBP0/OBP1/WY/WX after writing them; FF44 write remains ignored. Disable then re-enable at the observed guest bus phases yields documented emulator-policy reads LY=0, STAT mode 0 then mode 2. | Register fields/masks are documented; exact mid-line disable/re-enable hardware phase is not sourced for CPU-B and is asserted only as deterministic emulator policy. |
| `ppu_timing_partition` | Compare a halted whole run with segments crossing mode, VBlank and LY-wrap boundaries; require identical PPU event streams, guest-visible bus events, frame bytes, generation and completion time. A too-small instruction budget makes no device progress. | Metamorphic partition check; not independent hardware timing evidence. |

The implementation uses fixed per-instance storage: a 16-slot transfer queue, four two-dot fetch stages, at most ten selected objects, and fixed frame buffers. Queue entries identify bounded output-pixel slots; the common compositor resolves tile and object shade at emission. This supplies deterministic output pacing and bounded work, but it does not claim cycle-level equivalence of internal DMG FIFO contents or CPU-B fetch circuitry. The test-only PPU observer records mode changes, combined STAT rising edges, LY changes, and VBlank entry; public production APIs remain unchanged.

No case in this plan substitutes agreement with another emulator for hardware evidence. Any unlisted revision-sensitive effect is outside the claim and remains an evidence gap.
