## Summary

Scope was the diff `f5a3bd5..origin/main`. Review effort went to the C core and acceptance-stepper change, the release workflows and their trust wiring, and the verifier scripts. The long `verify-*` scripts were read selectively, not exhaustively. In particular `verify-historical-limitations.py`, `verify-support-ledger.py`, `verify-stall-report.py`, `verify-dense-input.py` and the rest of `verify-v02-delivery.py` and `verify-v02-performance.py` were not traced line by line. Their absence from the findings is not evidence that they are sound.

No BLOCKER was proven. Points checked and found sound:

- **Borrowed-span core seam** (`validate_accept_input_span`, the cursor accounting in `apply_input_events_now`, the batch copy through the 64-entry queue, `accept_span_output_is_disjoint`): the overflow-guarded range math, the reentrancy guards, the clearing of `accept_input_span` on every return path, and the validate-before-mutate ordering all hold.
- **Event-order semantics:** the `GBB_STOP_STOPPED` handling in the stepper matches the old queue-based semantics, apart from the replay divergence in WR-03.
- **Workflow triggers:** no `pull_request_target` or `workflow_run` trigger anywhere. Third-party actions are SHA-pinned.
- **Judge and attacher jobs:** `candidate-fuzz`, `candidate-corpus`, `candidate-performance`, `attach-v02-evidence`, `candidate-platform-manifest` and `publish-qualified-release` each check out the judge from `github.sha` at `trusted/` with `persist-credentials: false`. The write-holding attacher and publisher run only trusted-path scripts, and `verify-workflow-policy.py` enforces this.
- **Subject-controlled judge:** `verify-workflow-policy.py --self-test` includes a hostile-subject control (a subject-supplied judge and shadowed stdlib modules). The final evidence gate (`check_v02_evidence`) takes every delegated validator from `$ROOT` (the judge) and not from the subject checkout.
- **Downloads:** `download-release-artifact.py` has a byte cap, a total timeout and a stall timeout. It drops credentials on cross-origin redirects and only allows https, or loopback http when explicitly flagged.
- **Secrets and paths:** a scan of the in-scope files for home paths, emails and token patterns found only deliberate test-fixture strings.
- **PR-proof validator:** `verify-release-source-proof.py` now binds repository identity on the PR and on the check-runs, with negative controls.

The findings below are mostly trust-boundary gaps that the policy checker explicitly exempts, one cross-platform path-traversal gap, a retry path that cannot succeed once `main` moves, and fail-open or textual-only verifier patterns.

## Warnings

### WR-01: Source-executing release jobs keep a write token in env and a persisted checkout credential

**File:** `.github/workflows/release.yml:76,123-126,571,594-596,729,748-750`; `.github/scripts/verify-workflow-policy.py:716-727,986-1000`
**Issue:** `candidate`, `candidate-macos` and `candidate-windows` hold `contents: write`. They also set `GH_TOKEN: ${{ github.token }}` at job level, so every step sees it, including `cmake`, `cmake --build`, `ctest` and the tagged-tree `tests/scripts/*` verifiers. Their `actions/checkout` steps do not set `persist-credentials: false`, so the write token is also stored in `.git/config` of the workspace that builds and runs tagged code.

The policy checker classifies these jobs as role `residual` and applies none of its checks to them. `_check_checkout_credentials`, `_check_no_subject_execution` and `_check_unprivileged` run only for the producer, reader, attacher and gate roles.

15.1-DISPOSITIONS records `LIM-RESIDUAL-WRITE-JOBS` for "five write jobs" as an exactly enforced named set. That limitation covers the write authority itself. It does not cover the two cheap, independent hardenings that are absent here:
- the persisted credential;
- the job-wide token exposure.

`candidate-windows` and `candidate-macos` also run `tests/scripts/verify-release-candidate.sh` and `verify-v02-consumers.py` from the tagged workspace. Only `candidate` overlays the trusted copies. A compromised tagged tree can therefore alter what those jobs report while holding the token.
**Fix:**
- Add `persist-credentials: false` to the three checkouts and extend `_check_checkout_credentials` to the residual jobs.
- Move `GH_TOKEN` from job `env:` to the individual steps that call `gh`. No build, `ctest` or tagged-script step should receive it.
- Overlay trusted copies in the macOS and Windows jobs the way `candidate` does (`git show "$GITHUB_SHA:$path"`), or run those verifiers from a `trusted/` checkout.

### WR-02: `safe_extract_archive` does not reject backslash or drive-qualified members and is used on the Windows runner

**File:** `tests/scripts/verify-v02-consumers.py:303-309`; reached from `.github/workflows/release.yml:857` via `verify-release-candidate.sh --extract`
**Issue:** Path safety is judged with `PurePosixPath`. A member named `..\..\evil.txt` parses as the single part `('..\\..\\evil.txt',)`, so `".." in parts` is false. On Windows, `destination.joinpath(*parts)` resolves it to `C:\w\dest\..\..\evil.txt`, which escapes the destination. This was reproduced with `PureWindowsPath`. A component such as `x/D:evil` can also redirect to another drive. The check `parts[0].endswith(":")` only inspects the first component.

The old inline extractor had the same flaw, so this carries it forward, now in a shared helper. The sibling `.github/scripts/safe_extract_package.py:97` already rejects `"\\"`, so the project knows the rule. The archive being extracted is the downloaded draft asset, and the Windows job holds `contents: write` (see WR-01).
**Fix:** Reject, for every member, any `\\` in the name, any component containing `:`, and any component that is a Windows-reserved name:
```python
need("\\" not in member.name and all(":" not in p for p in parts), "archive-path-unsafe")
```
Add a negative control with a backslash-traversal member to the extractor self-test.

### WR-03: Diagnostic replay treats `GBB_STOP_STOPPED` as a hard failure where the main stepper resumes

**File:** `src/runner/acceptance.c:460-467` vs `src/accept/stepper.c:45-51`
**Issue:** The main drive (`advance_to_span`) now resumes a STOP-state machine when the borrowed span still has an event at or before the deadline and the window is not exhausted. This is the case where a non-waking event, such as a button press with the joypad interrupt masked, is followed by the wake event in the same window.

`replay_diag` drives the same borrowed span through `gbb_accept_run_diagnostic`, but any reason other than BUDGET, OUTPUT_FULL or HALTED_IDLE sets `status = 2` and breaks. For that script shape the main run completes and the diagnostic replay of the same script fails. The two paths were symmetric before this change: the old queue-based replay delivered the same events.
**Fix:** Mirror the stepper rule in the replay loop: on `GBB_STOP_STOPPED`, `continue` when `next_event < script->event_count && script->events[next_event].at_half_dots <= deadline && r.consumed_half_dots < budget`. Better, factor the rule into one shared helper so the two loops cannot diverge. Add a replay test for STOP followed by a non-wake then a wake event.

### WR-04: `retry` cannot succeed once `main` has moved past the release commit

**File:** `.github/workflows/release.yml:970-977` (and `verify_hosted` in `tests/scripts/verify-v02-fuzz.py`, which requires `git rev-parse HEAD == --source-sha`)
**Issue:** `candidate-fuzz` checks out `github.sha` at `trusted/` and then requires `git rev-parse HEAD == $SOURCE_SHA`. On a `workflow_dispatch` retry, `SOURCE_SHA` is the old tag's commit and `github.sha` is the current `main` HEAD, so the check fails with "BLOCKING LIMITATION". `attach-v02-evidence`, `candidate-platform-manifest` and `publish-qualified-release` all depend on this job, so the recovery path that `release-please.yml` offers (`retry`, `tag_name`, `source_sha`, `release_id`) can never reach publication unless nothing else has landed on `main`. The recovery logic added in `verify-published-release-assets.py` (draft-reuse, upload-missing) is unreachable in exactly the case it was built for.

A related budget problem: the job waits up to 90 x 30s (45 min) for the CI run and then `verify_hosted` polls up to 2700s, inside `timeout-minutes: 60`. A slow CI run therefore times out the job instead of failing with a diagnosable error.
**Fix:** Separate the trusted validator checkout from the source identity: check the verifier out from `github.sha` and bind the source SHA through the API, without requiring HEAD to equal it. For example, let `verify_hosted` read the tagged tree with `git show "$SOURCE_SHA:path"`. Otherwise remove or document the retry input as single-shot. Cap the combined wait below the job timeout.

### WR-05: `verify-uat-closure.py` enforces its contract with `assert`

**File:** `tests/scripts/verify-uat-closure.py:44-170` (24 `assert` statements; the other new verifiers use `raise`)
**Issue:** Every check in `check()`, `deliverables()` and the self-test's "mutation must be rejected" logic is an `assert`. Under `python -O` or `PYTHONOPTIMIZE`, all of them are stripped. `check()` then returns `total` having verified nothing, `self_test()` can never see an `AssertionError`, and it fails with "accepted weakened closure" or passes depending on the path. It is a gate whose docstring says "automated closure with zero human checkpoints", so a silently stripped gate is a fail-open defect. `python3 -I` ignores the env var, but direct and developer invocations (`tests/scripts/verify-uat-closure.py <dir>`, which the AGENTS.md workflow tells agents to run) do not necessarily use `-I`.
**Fix:** Replace the asserts with an explicit `Reject`-style exception (`raise ClosureError(msg)`) and catch that type in `self_test`. Add a guard at module import: `if not __debug__: raise SystemExit("verify-uat-closure must not run with -O")`.

### WR-06: Textual `find()` and substring checks still gate publication ordering and verifier behaviour

**File:** `tests/scripts/verify-release-candidate.sh:139-155`; `.github/scripts/verify-release-gates.sh:20-60` (the `check_config` heredoc)
**Issue:** `validate_publication_contract` uses `text.find()` on the first occurrence of the gate string and of the publish string, and asserts `gate <= publish` by byte offset. A YAML comment or a `|| true` variant before the real step satisfies it. A deleted or neutered real call is accepted as long as the string exists anywhere earlier in the file.

Its last check is `"json.loads(after_json)" in published_asset_verifier`, a textual grep of verifier source standing in for behaviour. `check_config` likewise counts route strings (`v02_route`, `aggregate_sidecar_route`) and substring-searches `delivery_source`. This phase added `verify-workflow-policy.py` precisely so wiring is judged from parsed jobs and reachable commands, and the file's own comment says so. These older text gates remain in `--self-test` and `check_config` and are duplicated pins of the same literals. They give false confidence and will drift. Note that `trusted/`-prefixed literals were edited in step with the workflow, which shows the coupling.
**Fix:** Delete the text-order checks that `verify-workflow-policy.py` now covers (`RELEASE_REQUIRED`, `publication-order`, `recovery-order`). Keep only data/contract checks such as `REQUIRED_ASSETS`. Replace the `json.loads(after_json)` grep with an executable control, which `recovery_self_test` already provides.

### WR-07: `workflow_job_id` sends the API token to whatever `GITHUB_API_URL` says and swallows every error

**File:** `tests/scripts/verify-v02-fuzz.py:311-335`
**Issue:** `api_base_url()` (line 726) states that `GITHUB_API_URL` "cannot select the authority being judged" and hard-codes `https://api.github.com` for qualification. `workflow_job_id()`, used when producing the receipt, ignores that rule: it takes `GITHUB_API_URL` from the environment with no scheme or host validation, attaches `Authorization: Bearer <token>`, and sends it there. A `http://` or foreign host would receive the job token.

The surrounding `except Exception: return None` then converts every failure to "no job id". The consumer does reject a receipt with no job id, so this fails closed, but the token exposure and the inconsistent trust model are real, and a bare `Exception` hides programming errors.
**Fix:** Reuse `api_base_url(test_fixture=False)` (or an allow-list of `https://api.github.com`) in `workflow_job_id`. Narrow the `except` to `(OSError, ValueError, urllib.error.URLError)`.

### IN-02: Legacy mode of `verify-published-release-assets.py` has a wrong usage string and an unhandled error path

**File:** `.github/scripts/verify-published-release-assets.py:321-327`
**Issue:** The usage text says `API_ASSETS_JSON BASELINE_JSON`, but `argv[0]` is treated as the JSON text itself (as `release.yml:1427` passes it). A malformed baseline file raises an uncaught `json.JSONDecodeError`/`OSError` traceback instead of `REJECT ...`. Also, the `published-verified` result of `decide()` is unreachable from `publish-qualified-release`. That job requires an unpublished draft at `--check-draft` before it ever calls `--check-recovery`, which would then hit "Unexpected recovery decision". The branch is only exercised by the self-test.
**Fix:** Correct the usage string to `API_ASSETS_JSON_TEXT BASELINE_PATH`. Wrap the baseline read in the same `(ValueError, OSError)` handler. Remove, or document, the dead published branch.

### IN-03: `PERFORMANCE_REGRESSION_REVIEW` is now a dead input with a misleading comment

After this phase the script ignores the note ("not an independent decision"). When the trigger fires the script exits non-zero (`qualify-v02-review-trigger-fired`), so the release job fails. ### IN-04: Two independent definitions of the 16384-event limit with no link

**File:** `src/core/gbb_accept_input.h:11` (`GBB_ACCEPT_INPUT_SPAN_MAX_EVENTS 16384u`) and `src/accept/gbb_accept.h:43` (`GBB_ACCEPT_SCRIPT_MAX_EVENTS 16384u`)
**Issue:** The script loader caps at one constant and the core validator at the other. If either changes, valid scripts silently become `GBB_STOP_INVALID_STATE` at run time (surfacing as `GBB_ACCEPT_DRIVE_STOPPED`) instead of being rejected at load time.
**Fix:** Add `_Static_assert(GBB_ACCEPT_SCRIPT_MAX_EVENTS <= GBB_ACCEPT_INPUT_SPAN_MAX_EVENTS, "...")` in a file that includes both (for example `stepper.c`).

### IN-05: `produce-release-evidence.sh collect` ignores dotfiles in the output directory

**File:** `.github/scripts/produce-release-evidence.sh:120`
**Issue:** `for entry in "$output"/*` does not match names beginning with `.`, so a stray `.hidden` file in the evidence output evades the "unexpected file" check. Impact is low because later steps address named files, but the check claims to prove an exact set.
**Fix:** Use `find "$output" -mindepth 1 -maxdepth 1` (or `shopt -s dotglob`) and compare names against `$EVIDENCE_NAMES`.

### IN-06: Invalid span leaves `*out_frame_count` stale in `gbb_run_audio_common`

**File:** `src/core/gabbaboy.c` (`gbb_run_audio_common`, the `span != NULL` validation block before `*out_frame_count = 0u`)
**Issue:** On a span-validation or overlap failure the function returns `invalid` before it zeroes `*out_frame_count`. Every other invalid return after the null check zeroes it first. The current caller initialises `written = 0` each iteration, so there is no live bug, but the output contract now differs by failure kind.
**Fix:** Move `*out_frame_count = 0u;` to immediately after the `out_frame_count == NULL` check.

### IN-07: `${{ }}` interpolated into `run:` bodies

**File:** `.github/workflows/release.yml:270,332` (`${{ steps.identity.outputs.version }}`, `${{ steps.identity.outputs.release_id }}` inline in scripts; also `909,918` with the run nonce)
**Issue:** The inline values are produced by validated steps (tag regex `^v[0-9]+\.[0-9]+\.[0-9]+$`, numeric release id, generated nonce), so no injection is possible today. The rest of the file consistently passes values through `env:`, and `verify-workflow-policy.py` does not forbid `${{` inside `run:` text. A later edit that routes an unvalidated output through the same pattern would be unchecked.
**Fix:** Pass through `env:` like the other steps, and add a policy check rejecting `${{` in `run:` for any expression that is not `github.run_id`, `github.run_attempt` or `github.sha`.

### IN-08: Verifier scripts depend on a user-home runtime and persisted read tokens

**File:** `tests/scripts/verify-closeout-scan.py:25,30-32`; `.github/workflows/ci.yml`, `fixture-repro.yml`, `preview.yml` (checkouts without `persist-credentials: false`; only the `linux-sanitizers` job is policy-enforced)
**Issue:** `verify-closeout-scan.py` locates the runtime from `$CODEX_HOME/gsd-core/bin/gsd-tools.cjs` (default `~/.codex`) or an arbitrary `GSD_TOOLS` path and executes it with `node`. It is therefore non-hermetic, and its check depends on whichever runtime the invoking user has installed. The script does verify package identity and hashes the entry point, which mitigates impersonation. Separately, most `ci.yml`, `fixture-repro.yml` and `preview.yml` checkouts leave a read-only token in `.git/config`. The risk is low, since the token is read-only, but the choice is inconsistent with the stated policy.
**Fix:** Document the runtime requirement in the test registration, or skip with an explicit "unsupported" code when the runtime is absent. Set `persist-credentials: false` on the remaining checkouts.
