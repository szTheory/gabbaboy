# Phase 15.1 Plan 22: Residual release jobs step-scoped token and trusted overlay Summary

The three tagged-code-executing residual release jobs now hold the write token only on `gh` steps, check out without a persisted credential and replace the tagged verifiers with the workflow commit's copies before first use; the policy judge enforces all of it from the parsed workflow (WR-01).

## Accomplishments

- **Task 1 (tracer, commit 5e60f3d).** candidate-windows end to end: job-level `GH_TOKEN` removed, token on the identity, select, attach and download steps only, `persist-credentials: false` with `fetch-depth: 0` kept, and an overlay step before the qualify step. The judge gained `SUBJECT_EXECUTION` (hoisted from the attacher rule), `_check_token_scope`, `_check_token_subject_execution`, `_check_trusted_overlay`, `TRUSTED_OVERLAYS` and a residual branch. Negative controls 80 to 85.
- **Task 2 (commit 99df5bc).** Same split in candidate (the identity, merged-PR proof, source receipt, retry fetch, archive append, draft download, consumer receipt attach, source-archive receipt attach, candidate receipt fetch and attach, and final-download steps are tokened; the build, revalidate, smoke, consumer proof, archive inspect, receipt verify and final verify steps are not) and candidate-macos (identity, select, attach and download tokened; build, player build and smoke not). Candidate overlays `verify-v02-consumers.py` as a fourth path. candidate-macos gained the two-verifier overlay before its first `--extract` call. `_check_residual_classification`, `RESIDUAL_SUBJECT_JOBS` and `TOKEN_SCOPE_EXEMPT` added; negative controls 85 to 101.
- **Step splits that moved logic.** The retry revalidation, build-receipt write, candidate receipt write/verify and consumer receipt flow now communicate through `CANDIDATE_REUSED` and a new `CANDIDATE_RECEIPT_EXISTS` value in `GITHUB_ENV`; command text of every required call is unchanged.

## Deviations from Plan

**1. [Rule 2 - Missing critical functionality] Per-step token coverage is cross-checked outside the judge**
- **Found during:** Task 2
- **Issue:** The judge proves a tokened step runs no subject code but cannot prove an untokened step has no `gh` call. A missed `gh` step would fail only at release time.
- **Fix:** A one-off parse of the three jobs confirmed every step with a `gh` command carries `GH_TOKEN` and no other step does (0 mismatches). Recorded as D1 evidence; not added to the judge.
- **Files modified:** none

**2. [Plan-detail] Overlay steps use explicit per-path lines rather than a loop**
- **Found during:** Task 1
- **Issue:** The shell reader drops loop headers, so a `for path in ...` overlay cannot be proved by parsed events.
- **Fix:** candidate's existing loop was rewritten as four explicit `git show` lines, with `verify-v02-consumers.py` added.
- **Files modified:** .github/workflows/release.yml
- **Commit:** 99df5bc

**3. [Plan-detail] Draft and tag recheck moved to the attach step**
- **Found during:** Task 2
- **Issue:** The recheck sat in the same step as `cmake --version` and `tests/scripts` calls, so it cannot share a step with the token.
- **Fix:** Moved to the tokened step directly before `gh release upload` (see key-decisions).
- **Commit:** 99df5bc

**Total deviations:** 1 auto-added check (Rule 2, no code change) and 2 plan-detail adjustments. **Impact:** none on scope; every required command text is unchanged.

## Limitations kept explicit

- The hosted proof is the parsed policy judge only; release.yml runs only on a release and no release was created (P15-01 stays an explicit residual).
- The judge cannot see the redirect target of an overlay `git show` line (the reader drops redirects), so it proves the workflow-commit copy is produced before first use, not that it is written to the same path.
- LIM-RESIDUAL-WRITE-JOBS is unchanged: the five residual jobs still hold `contents: write`; that stays an owner decision.
