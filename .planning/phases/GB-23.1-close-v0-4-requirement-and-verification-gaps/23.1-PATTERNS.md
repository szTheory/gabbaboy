## Pattern Assignments

### tests/scripts/verify-planning-hygiene.py — protected-root validation

**Analog:** frontmatter_duplicates (lines 360–390), frontmatter_fields (340–358), _frontmatter_root_key_is_alias (513–543), and frontmatter_mapping_pairs (545–572).

The current duplicate scan extracts only supported plain keys through parse_frontmatter_plain_key. The alias recognizer checks YAML-equivalent forms for the requirements mapping, but other readers consume phase, unresolved_gates, and requirement_dispositions through separate paths. D-202 requires one shared pre-consumption guard for every protected root. Retain the fixed-schema rule: canonical column-zero root spellings are accepted; quoted, decorated, explicit-key, aliased, duplicate, or unsupported protected-root spellings are rejected before their values are read.

Existing duplicate evidence is retained before a dictionary is populated:

    if key is not None:
        if key in top_level:
            duplicates.append(f"top-level key '{key}'")
        top_level.add(key)

Extend that same early-validation pattern rather than normalizing alternate YAML spellings into accepted keys. Keep the existing stable report refusal families and distinguish a duplicate from a lone alias that makes a required root absent. The official YAML 1.2.2 specification documents unique mapping keys, node properties before key content, aliases, quoted scalar keys, and explicit block keys; the locked repository contract deliberately rejects those alternatives instead of implementing their full semantics.

**Adversarial failure to avoid:** updating only frontmatter_mapping_pairs leaves the sequence and object roots exposed. Likewise, teaching frontmatter_fields to consume quoted keys without making duplicate detection use the same interpretation can hide a conflicting key again.

### tests/scripts/verify-planning-hygiene.py — disposition rows

**Analog:** frontmatter_objects (lines 421–453), frontmatter_duplicates (360–390), and the exact expected-disposition comparison in check_v04_report (845–860).

The current object reader starts an item only when the row matches its narrow item-key expression. A nonblank unsupported list row is otherwise skipped; nested fields are also ignored while current is None. This is the CR-06 path: an extra row such as a spaced or tabbed id key can disappear before actual_dispositions is compared with the expected four records.

Keep the fixed object grammar and make row accounting total: every nonblank row in the protected sequence must parse as an object item or a supported nested field, or cause the reader to refuse. Using the same key rule as duplicate validation is also valid if unsupported rows still fail closed. Do not silently omit a row or accept a partial object. The report-stage contract already compares the complete ID/status/owner set and converts a refusal into the existing v04-report-requirements failure family.

    for line in lines[start + 1:]:
        if line and line[0] not in " \t":
            break
        item = re.match(r"^[ \t]*-[ \t]+([A-Za-z0-9_-]+):[ \t]*(.*?)[ \t]*$", line)
        if item:
            if current is not None:
                entries.append(current)
            decoded = decode_frontmatter_scalar(item.group(2))
            if decoded is None:
                return None
            current = {item.group(1): decoded}
            continue
        field = re.match(r"^[ \t]+([A-Za-z0-9_-]+):[ \t]*(.*?)[ \t]*$", line)
        if field and current is not None:
            decoded = decode_frontmatter_scalar(field.group(2))
            if decoded is None:
                return None
            current[field.group(1)] = decoded

This excerpt shows the current reader shape; its missing fallback is the D-202 concern. Keep any implementation local to this existing reader; no parser module or general YAML implementation is needed.

## Shared Patterns

### Narrow fixed-schema parsing

Keep the implementation in the existing Python standard-library checker. Preserve duplicate pairs until checked, reject unsupported syntax before reading values, and require complete object rows. Do not add a general YAML parser or dependency: the report has a known schema, and broader parsing adds accepted syntax and dependency surface without helping this contract.

### Immutable inputs and causal tests

Historical report/handoff evidence is read from full commit IDs. Reuse the disposable Git commit and production CLI pattern. Assert the specific refusal class and pair malformed inputs with valid canonical twins so an unrelated error cannot make a negative appear effective.

### Bounded check order

During execution, run direct syntax/self-test controls first, then immutable report and handoff checks, the 125/124 wrapper boundary, SUMMARY coverage, and shared UAT closure. Only after those pass, configure the existing phase1 preset and run plan_cap plus planning_hygiene_controls. No broad suite, extra lifecycle retest, or D-103 suite is in scope.

### Inherited constraints

The prior map's Markdown visibility findings remain valid historical contracts: preserve the shared code/comment-aware line mask, LF-only Markdown splitting, ATX boundaries, and existing Setext refusals. D-202 does not authorize changing those paths. Task 9 also established the current strict scalar decoder and YAML line handling; retain their controls unchanged.
