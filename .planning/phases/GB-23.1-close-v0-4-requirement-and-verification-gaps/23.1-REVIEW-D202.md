### CR-07: Non-ASCII indented disposition rows terminate parsing silently

**Severity:** Critical (BLOCKER)
**File:** tests/scripts/verify-planning-hygiene.py:408-423, 482-495, 901-908
**Classification:** BLOCKER
**Issue:** frontmatter_objects breaks out of requirement_dispositions whenever a nonblank line begins with a character other than ASCII space or tab. With an extra row after the four canonical entries whose indentation begins with a non-breaking space, line[0] not in " \t" is true and the parser returns only the four canonical entries. frontmatter_duplicates also treats that row as a new root line; the plain-key parser and protected-root alias matcher do not recognize the non-breaking-space prefix, so no duplicate is reported. The report consumer then compares the four retained entries with the expected set and can accept the document while silently ignoring the contradictory row. This is an unsupported-indentation variant of the false-acceptance path CR-06 was meant to close.

**Fix:**
~~~python
if line and line[0] not in " \t":
    if parse_frontmatter_plain_key(line) is None:
        return None
    break
~~~
Treat a nonblank line with an unsupported prefix as a refusal while parsing the protected object block. Add a production-CLI negative using a non-ASCII indentation character before an extra disposition row, paired with the canonical positive.
