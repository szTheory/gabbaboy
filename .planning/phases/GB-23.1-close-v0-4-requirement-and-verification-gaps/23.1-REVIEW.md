## Critical Issues

### CR-05: Quoted YAML root aliases can hide duplicate protected keys

**Severity:** Critical
**File:** `tests/scripts/verify-planning-hygiene.py:312-315, 340-356, 360-391, 394-418, 513-557, 823-848`

**Issue:** The duplicate scanner and field reader recognize only plain ASCII root keys. The YAML-equivalent quoted-key, anchor/tag, and explicit-key forms are ignored for `phase`, `unresolved_gates`, and `requirement_dispositions`. For example, a report can contain both `"phase": GB-21-cgb-game-progress-and-scene-regressions` and the canonical `phase: GB-22-composition-and-microtest-evidence`. `frontmatter_duplicates` ignores the quoted key, `frontmatter_fields` ignores it and returns the canonical value, and the report check accepts the conflicting duplicate. The custom YAML-alias detector is applied only by `frontmatter_mapping_pairs` to the `requirements` root, so the sequence and object consumers have the same gap.

**Fix:** Before any reader consumes protected frontmatter, detect equivalent spellings of every protected root key, including quoted, anchored/tagged, and explicit-key forms, and refuse any noncanonical alias or duplicate. With the fixed-schema, standard-library parser, fail closed on unsupported root-key syntax. Add causal production-CLI negatives for aliases before and after canonical roots and assert the report duplicate/root refusal family.

### CR-06: Spaced disposition item keys are silently omitted by the object reader

**Severity:** Critical
**File:** `tests/scripts/verify-planning-hygiene.py:381-390, 421-454, 848-856`

**Issue:** `frontmatter_duplicates` recognizes a sequence item key with spaces or tabs before its colon (`- id : EXTRA-01`), but `frontmatter_objects` requires the colon to immediately follow `id`. An extra row placed before the four canonical dispositions, such as `- id : EXTRA-01` with nested `status` and `original_owner` fields, is therefore treated as a new item by the duplicate scanner but skipped by the object reader. Because no current object exists yet, the nested fields are ignored too. The reader returns only the four later canonical rows, so `actual_dispositions` matches the expected set and the production report check accepts a document containing an extra contradictory disposition.

**Fix:** Make the disposition item reader use the same shared key parser as duplicate detection, or reject any nonblank sequence row that does not match the supported object grammar. Add a production-CLI negative with a spaced/tabbed `id` key and an otherwise valid extra disposition before and after the canonical rows.
