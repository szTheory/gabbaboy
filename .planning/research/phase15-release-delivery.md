## Exact-tag v0.2.0 release delivery and safe automation

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Pinned release-please + `GITHUB_TOKEN` + exact-tag draft, downloaded-byte gate, one publish | Keeps version/changelog review in a PR; the pinned action exposes the tag and tagged SHA ([release-please v5.0.0 at the repository's full-SHA pin](https://github.com/googleapis/release-please-action/blob/45996ed1f6d02564a971a2fa1b5860e934307cf7/README.md)); existing `release.yml` builds from that exact source, retains separate PR-head/merge/tag identities, validates a source receipt and platform receipts, downloads and smoke-tests the draft bytes, then publishes once. GitHub recommends draft → attach assets → publish for immutable releases ([GitHub guidance](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)). | A `GITHUB_TOKEN`-created PR's `opened`/`synchronize`/`reopened` workflow runs require a write user's approval ([GitHub token behavior](https://docs.github.com/en/actions/concepts/security/github_token)); an interrupted pre-publish run can leave a partial draft; a post-publish readback failure is already past the one-way boundary. | Existing `.github/workflows/release-please.yml`, `release.yml`, and proof helpers; no core dependency — risk: mixing PR head, merge SHA, tag SHA, or a partially attached asset set. | Rec if exact-tag provenance, downloaded-package qualification, and bounded recovery are release requirements. |
| Same staged flow with a narrowly scoped GitHub App installation token | Lets release-please-created PR checks run without the `GITHUB_TOKEN` approval pause; preserves the existing required-check, draft, download-smoke, and publication gates. GitHub documents an App installation token as an alternative when automation must trigger follow-up runs. | Requires a trusted App installation, private-key secret, token minting, and least-privilege permission review; no App credential is evidenced in the current repo state; it still cannot substitute for branch protection or passing exact-head checks. | Token creation and release-please permission wiring — risk: credential leakage or excess token scope. | Rec if the owner requires unattended release-PR checks and can provision an appropriately scoped App; otherwise keep the documented run-approval gate. |
| Build on an exact-tag CI run, then promote its workflow artifact into the release draft | Avoids a second build if the tag-run artifact is itself the qualified build; a promoter can still verify the run SHA, digest, downloaded consumer smoke, and draft state. | Current preview artifacts are PR-head outputs with 14-day retention (player candidate retention is 1 day), not exact-tag release outputs; Actions artifacts expire and therefore cannot be the durable release copy ([GitHub retention docs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)). Promotion would need a new tag-bound producer and must carry artifact/run identity through every check. | New tag build/upload and cross-run promotion path — risk: expired artifact, wrong run/SHA, or smoke evidence attached to different bytes. | Rec if a future exact-tag CI artifact is already built and smoke-qualified with retention covering the release window; not for reusing today's PR preview artifact. |

**Rationale:** The current staged pipeline best matches SHIP-11 while reusing the repository's flat, project-owned proof helpers. On 2026-10-16, PR [#70](https://github.com/szTheory/gabbaboy/pull/70) was open at head `aaeb039f339513021c288454f257f684e1c547c9` against base `c771b1b9c143d7589f8bb40c163c2e9f89ca1168`, marked `BLOCKED`, with no checks reported; its [CI](https://github.com/szTheory/gabbaboy/actions/runs/38904634046), [preview smoke](https://github.com/szTheory/gabbaboy/actions/runs/38904634043), and [fixture reproduction](https://github.com/szTheory/gabbaboy/actions/runs/38904633896) runs were `action_required`. This is an approval-to-run gate, not a test result or a manual UAT checkpoint. An authorized agent with write permission can attempt approval for these current waiting runs; involve the owner only if permissions or credentials actually prevent that action. Then require all three checks to pass on the final PR head; preserve the release PR head, squash-merge SHA, release-please tag/source SHA, and package digests as separate identities. The existing source receipt and [`verify-release-source-proof.py`](../../.github/scripts/verify-release-source-proof.py) recheck the merged PR and exact-head GitHub Actions contexts; [`release.yml`](../../.github/workflows/release.yml) supplies reusable clean-tagged-source, matching-draft/tag/source, complete-platform-output, downloaded-byte consumer/player smoke, generic support-sidecar, performance-receipt, and final API-readback mechanisms. It does not implement the Phase 15 CGB support ledger/schema or a DMG-vs-v0.1 A/B comparison: the current support validator still uses the v0.1 contract, while the existing `release-performance-receipt` is trace/no-trace digest equality and hosted durations. Phase 15 must add an exact `v0.2.0` ledger assertion and compatibility evidence. The exact-head `required-native` run invokes `run-bounded-fuzz.sh --fast` in [`ci.yml`](../../.github/workflows/ci.yml), but that mode can pass deterministic checks when the libFuzzer runtime is unsupported, and the sanitizer job does not pin/verify Clang. Thus Phase 15 needs evidence of a real Clang/libFuzzer campaign plus a source-bound campaign receipt, alongside a new measured DMG-vs-v0.1 performance comparison; existing runners and receipt helpers are reusable plumbing, not evidence these criteria are already met. The [`verify-support-ledger.py`](../../tests/scripts/verify-support-ledger.py) intentionally falls back to the newest ledger at or below a tag, so omission of `docs/support/v0.2.0.md` could silently bind the v0.1 ledger. CGB-11 is satisfied either by the rights-clear scripted game acceptance or by explicitly recording that no CGB game-level evidence exists; neither Phase 14 corpus results nor an image alone qualify a game. Keep retries limited to the same draft ID, tag, and source SHA: revalidate and reuse byte-identical receipts/assets, fail closed on partial or changed uploads, and never replace public assets; if publication succeeds but readback fails, inspect the release before any retry and use a later version for corrections. Also close D-051 at the boundary: GitHub's automatic tag source archives are generated separately from attached product packages and currently include `fixtures/mooneye-mbc` (17 MiB raw, roughly 33 KiB compressed); [`verify-release-source-proof.py`](../../.github/scripts/verify-release-source-proof.py) proves source/PR/check identity but does not verify that archive's contents. Retain and document the licensed test-fixture source archive, or use Git's `export-ignore` and add an archive-content contract ([GitHub source archives](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives), [Git `export-ignore`](https://git-scm.com/docs/gitattributes#_export_ignore)). Keep the current explicit unsigned/notarized-false status; signing would need its own provisioned Developer ID flow and verification of final distributed bytes ([Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)). At this snapshot there was no `v0.2.0` tag/draft and no open issue; main CI for `c771b1b` was still running, so no release readiness is inferred.
