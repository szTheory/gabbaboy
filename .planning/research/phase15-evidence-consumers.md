# Phase 15 Evidence Closure Route

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| **Split, source-bound release evidence** (versioned support ledger plus separate consumer, fuzz and performance receipts) | **QA:** extends the tag-aware ledger proof and keeps eligible/executed cases, actual guest passes, matched expected failures and exclusions distinct; **C/API:** reuses installed C/C++ consumers that already test profile selection, ROM probe, RGB555 stride/profile errors and RTC catch-up/error behavior; **host/security:** relocated `find_package(GabbaBoy)` consumers cover installed-package use and negative twins; **performance:** existing A/B harness interleaves runs and checks a fixed workload/output digest; **product/legal:** ledger can say clearly when CGB game-level or physical-hardware evidence is absent. Consumer source-level success is not a stable ABI promise. Pending prose is chronological and must be reconciled rather than appended. | Existing docs, consumers and scripts; add versioned ledger dispatch plus source/build/campaign receipt checks -- Risk: stale prose or unsupported runs mistaken for release evidence. | Rec if Phase 15 remains a bounded v0.2 release with evidence classes kept separate. |
| **Generated release dossier from one evidence registry** | **QA:** a single validated record could render support prose and tagged sidecar; **C/API/host:** consumer receipts could be linked to exact source; **security/performance/legal:** one schema could require provenance and visibly render exclusions or missing evidence. | Adds a registry and renderer beside existing receipt schemas; duplicates corpus, benchmark and fuzz producers; increases maintenance and mutation surface, with risk that a structurally complete generated report hides conflated evidence. | New schema, renderer, contract tests and release wiring -- Risk: duplicated truth and broader release-tooling failure surface. | Rec if future releases need recurring machine-generated reports for several channels. |

**Rationale:** Reuse the tag-aware support flow but preserve its strict v0.1 behavior: `verify-support-ledger.py` currently fixes the DMG model, three cases, four manifests and an empty failure list, so v0.2 should dispatch by schema/version and validate its own bounded model/corpus structure with negative controls, not relax those checks. Phase 14’s [closure receipt](../phases/GB-14-cgb-e-model-qualification-and-corpus/14-CLOSURE.md) records 107 completed cases: 25 actual guest passes and 82 matched expected failures; evaluator success and xfails must not be counted as guest passes, while physical CGB-E remains UNKNOWN/POLICY. The existing [C](../../tests/consumers/c/main.c) and [C++](../../tests/consumers/cpp/main.cpp) consumers already exercise SHIP-10’s behavioral discriminators, so repeat them from a relocated install at the evidence head and close any documentation/receipt gap; CMake’s [package guide](https://cmake.org/cmake/help/latest/manual/cmake-packages.7.html) describes installed exports as relocatable packages. For SHIP-11, use **v0.1.0** as the baseline (tag commit `e30d168f7fc61de8db0a3801e7b1736362912cb7`): source inspection on 2026-10-16 found `tests/measure_core.c` at that tag with the same `original-wram-tracer-1m-half-dots-v1` one-million-half-dot workload contract as the current harness. The benchmark job must still run the tagged binary and verify workload and output digest; if that runtime check fails, use a measurement-only adapter linked against the untouched v0.1 core, never relabel new-core results. Build both binaries from clean tag/commit checkouts, bind recorded revisions to those checkouts and binary/build identities, and require same host/compiler/flags, workload, paired warmups/samples, digest and reported uncertainty. Reject unknown revisions or incompatible builds, and reconcile the candidate receipt to the eventual v0.2.0 tag SHA. Treat the historical loaded-host Phase 10 percentage only as context; Google Benchmark’s [upstream guide](https://github.com/google/benchmark/blob/main/docs/user_guide.md) documents warmups and repeated-run statistics, without requiring that dependency here. A local missing libFuzzer runtime is a routing condition, not SHIP-11 evidence: source inspection of the existing [Linux ASan/UBSan job](../../.github/workflows/ci.yml) shows its sanitizer preset does not pin Clang, while `run-bounded-fuzz.sh --fast` can succeed after reporting unsupported. Route a real bounded campaign through that existing Linux job using a Clang/libFuzzer build, retain an exact-source campaign receipt and require an actual fuzz result; deterministic regressions and `unsupported` alone do not satisfy refreshed fuzzing. This is an inference from workflow/configuration source, not an observed hosted run; if no eligible host produces the campaign receipt, leave SHIP-11 and release gate open. LLVM’s [libFuzzer guide](https://llvm.org/docs/LibFuzzer.html) states the matching-Clang requirement and `-max_total_time` bound. For product/legal closure, reconcile pending entries against the final corpus and release state, state CGB game-level evidence only after per-candidate rights closure (otherwise explicitly state its absence), and audit third-party notices plus source-archive contents; SPDX’s [license list](https://spdx.org/licenses/) provides identifiers but does not establish rights for a particular game asset. Primary documentation checked 2026-10-16. Follow-ups: versioned ledger dispatch; tagged count/claim refresh; relocated installed consumers; exact-tag v0.1.0/current performance comparison; bounded exact-source Linux fuzz receipt or an open release gate; chronology and notice reconciliation.
