# Phase 15.1 Plan 33: Workflow policy judge, device names and closeout runtime Summary

The workflow policy now refuses tagged-tree command heads nested anywhere in a token-holding residual step, late or hidden verifier first use, and weakened release guards; archive extraction refuses every Windows device name; the closeout scan no longer falls back past an explicit GSD_TOOLS.

## What changed

- Task 1 (2519f2a): `_tokens` and `shell_events` gain a keyword-only `extended` mode used only by the token judge and the overlay rule. It reads `(( ))` as one word, folds `name=( ... )` into one assignment word, and logs each heredoc as (delimiter, quoted, body). Default mode is unchanged. New `TOKEN_STEP_COMMANDS`, `TOKEN_STEP_TRUSTED_OPERANDS`, `_backticks`, `_token_command_allowed`, `_token_step_commands` (recursive, converts any parse failure to `token-subject-execution`, rejects an unquoted heredoc whose body expands, rejects an unclosed `[[`) and `_check_token_step_commands`, called for the five residual-role jobs at the end of `check_release` with a comment naming why candidate-fuzz and attach-v02-evidence are outside it.
- Task 2 (d57305a): `_check_trusted_overlay` reads every step up to the last overlay step with the extended reader (fail closed as `trusted-verifier-overlay`), matches first use by basename with quotes and variable prefixes stripped, and skips `git show` events. `RELEASE_GUARD_EXPRESSIONS` plus `_normalise_if` pin the four job guards and five reuse step guards for exact comparison; the old fragment checks run first.
- Task 3 (6435cdf): `WINDOWS_RESERVED_NAMES` gains CONIN$ and CONOUT$ and `windows_unsafe_member` compares the NFKC-normalised stem. `installed_tools` raises `runtime-unavailable` naming GSD_TOOLS when it is set and not a file. The comment above the published-state branch of `decide()` now states the real reachability (GR-IN-03 evidence only; no behaviour change, GR-IN-03 stays deferred in 15.1-36).

## Re-enumerated tokened-step commands and trusted operands

Heads found by the extended parser in token-holding steps of the five jobs, including nested bodies: set, echo, exit, printf, gh, jq, mkdir, cmp, cp, git, basename, bash, base64, sed, head, read, cat, python3. Final `TOKEN_STEP_COMMANDS`: gh, jq, cmp, echo, printf, set, exit, mkdir, cp, cat, read, basename, base64, head, sed (every entry is used in the real tree; test, [, true, false and : were not needed and are absent). Exceptions the real tree needs: `bash trusted/.github/scripts/verify-release-gates.sh`, `bash build/verify-release-gates.sh`, `python3 -I trusted/.github/scripts/*.py`, `python3 - args` (stdin), `git show ${GITHUB_SHA}:...`, `git rev-parse`, `git status --porcelain`. Trusted operands: prefix `trusted/` and the exact path `build/verify-release-gates.sh`; any operand with a `..` segment is refused.

## Residual GR-WR-03(a)-R

GR-WR-03 is closed_with_residual, not fixed. Scope of the judge: the five residual-role jobs (candidate, candidate-macos, candidate-windows, candidate-platform-manifest, publish-qualified-release). candidate-fuzz (trusted-reader) and attach-v02-evidence (attacher) are excluded because their only checkout is the trusted workflow revision (ref github.sha, path trusted, persist-credentials false, enforced by `_check_trusted_checkout`) and they never check out or build the tagged tree. The judge is defense in depth for the command-execution channel; it is linked to owner limitation LIM-RESIDUAL-WRITE-JOBS, whose structural fix (removing the token from jobs that read the tagged tree) is the owner decision. The limitation is not marked accepted or passed. Six channels are deliberately unjudged and have no rule, constant entry or mutation:

- A. Interpreter or script source read from data: `python3 -` fed tagged bytes on stdin; `sed -f` with a file or stdin script.
- B. Writes into a trusted path before a trusted-operand run: `cp x trusted/.github/scripts/verify-release-gates.sh`, a redirect onto `build/verify-release-gates.sh`, or `gh release download --dir trusted/...` or `--dir build` followed by `bash` on it.
- C. Environment hijack: `PATH=build:$PATH`, `BASH_ENV=...`, appending a directory to `$GITHUB_PATH`, or `echo "BASH_ENV=$PWD/build/x" >> "$GITHUB_ENV"` consumed by a later step.
- D. `gh alias set`, `gh extension install`, and `gh config set` of browser, editor or pager.
- E. Arithmetic or prompt-expansion evaluation of tagged bytes: `(( x ))`, `$(( x ))` or array subscripts whose value is tagged text, `${var@P}`.
- F. sed's `e` command and `s///e` flag, which run pattern-space text as a shell command although sed stays allowlisted: `sed '1e ./build/x --version' /dev/null` and `echo a | sed 's/a/./e'`.

## Deviations from Plan

- [Rule 3 - Blocking] The plan did not say where in `check_release` to call the judge. Calling it beside `_check_token_subject_execution` made existing mutations (for example "release manifest judge taken from the subject checkout", and mutations that replace a tokened step with `run: true`) fail with `token-subject-execution` instead of their expected codes. The call now sits at the end of `check_release` so every existing diagnostic keeps priority; `true` is not added to the allowlist.
- GR-IN-03 is a comment correction only; it stays deferred in 15.1-36.
- Task 3 was committed as one commit (the TDD red result was observed and recorded, not committed separately).
