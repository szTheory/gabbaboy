## Summary

All of CONTEXT.md's decisions are implementable as locked, with **eight factual corrections** that the planner must absorb (see "Corrections to CONTEXT.md premises" below). The most consequential: (1) the Windows lane compiles with **MinGW-w64 GCC 14.2 + Ninja, not MSVC**, and the core is a static library, so there is no MSVC import/export surface to claim; (2) **no existing player test asserts the "2 MiB read bound" message** (the "oversize" test writes 32,769 bytes), so the P3 IN-01 evidence gate in D-05 does not exist yet and a new assertion must be added; (3) the conflict-marker lesson is GB-GSD-**011**, not 010.

The GitHub semantics needed for D-07 are confirmed by docs plus a live probe of this repository's Actions history. A re-run keeps the **same run id and `run_number`**, bumps **`run_attempt`**, and the list endpoint returns **one entry per run id reflecting its latest attempt**, newest first. Job lists default to the latest attempt (`filter=latest`); `filter=all` returns jobs from every attempt, so a predicate reading `filter=all` must also check the job's `run_attempt`. Because re-runs do not create new run ids, the IN-02 bug only occurs when a *different* run (a `reopened` event or duplicate trigger) exists for the same head SHA, which is exactly what "newest run decides" fixes.

`gbb_reset` demonstrably clears all APU state: `reset_state` zeroes the pulse/wave/noise channels, NR50/NR51/power, the sequencer step, sample phase, the event ring, mix levels and HPF state, and resets `time_half_dots`. A throwaway program compiled against the in-tree core confirms that a post-reset re-run produces the identical FNV-1a hash as a fresh instance. **The reset-hash assertion is therefore permitted by D-03.** Phase 06.1 will make all six phases' verification reports stale (measured below), so the refresh PR is mandatory, not optional.

**Primary recommendation:** Implement the gate as a single Python 3 stdlib script (`.github/scripts/wait-exact-head-ci.py`) that shells out to `gh api` with the SHA passed as argv (never interpolated into a filter), unit-tested by `--self-test` via injected fetch/sleep/clock; wire the self-test as one new step in the `native-linux` job of `ci.yml`; add `audio_api_smoke()` to both consumers using the numbers in "Audio consumer smoke"; land all workflow edits in one commit.

### Pattern 1: Exact-head gate predicate (locks D-07)

**What:** a pure function `decide(sha, runs_response, fetch_detail, fetch_jobs, state) -> WAIT|PASS|FAIL` driven by a thin loop. All I/O is injected so `--self-test` runs canned JSON with a fake clock.

**Per-poll algorithm (evidence-backed):**
1. Validate `sha` against `^[0-9a-f]{40}$` before any network call.
2. List: `GET repos/{repo}/actions/workflows/ci.yml/runs?head_sha={sha}&event=pull_request&per_page=100`. If `total_count > len(workflow_runs)` -> FAIL (truncated; fail closed).
3. Filter locally (belt and braces): `head_sha == sha and event == "pull_request" and path == ".github/workflows/ci.yml"`. Empty -> WAIT.
4. `newest = max(filtered, key=run_number)`. (One entry per run id at its latest attempt; see semantics below.)
5. Detail: `GET repos/{repo}/actions/runs/{id}`. If `run_attempt`, `head_sha`, `event`, `path`, `status` disagree with the list entry -> WAIT (in flux; deadline fails closed).
6. `status != "completed"` -> WAIT.
7. `conclusion == "success"` -> fetch jobs `GET .../runs/{id}/jobs?filter=latest&per_page=100`; for every required name require exactly one job with that name and `conclusion == "success"`; missing or non-success -> FAIL (not debounced, the run is already completed and success-claiming).
8. Any other conclusion (`failure`, `cancelled`, `timed_out`, `action_required`, `neutral`, `skipped`, `stale`, `startup_failure`) -> require the same `(run_id, run_attempt)` failing on **two consecutive polls** before FAIL; otherwise WAIT. A different `(id, attempt)` resets the counter.
9. Deadline (keep: Linux/macOS 1500 s, player 1800 s; interval 10 s) -> FAIL with the existing message text.

**Player mode** additionally requires `macos-player-package` success and writes `run_id` and `run_attempt` to `$GITHUB_OUTPUT` (see Pitfall 3 for which attempt number).

**Interface sketch (not final):**
```
python3 .github/scripts/wait-exact-head-ci.py \
  --sha "$EXPECTED_SHA" --repo "$GITHUB_REPOSITORY" \
  --require required-native [--require macos-player-package] \
  --deadline-seconds 1500 [--github-output "$GITHUB_OUTPUT"]
python3 .github/scripts/wait-exact-head-ci.py --self-test
```
Pass the SHA as a CLI argument; the current inline code interpolates `${EXPECTED_SHA}` into a jq program (preview.yml:31-32), which is only safe because the head SHA happens to be a hex string. The player job validates it (preview.yml:156-159); the Linux/macOS jobs do not.

### Pattern 3: Single-source player gating in `ci.yml` (P2 IN-01)

Facts that constrain the design:
- `jobs.<job_id>.if` can read only `github, needs, vars, inputs` [CITED: docs.github.com/en/actions/reference/workflows-and-actions/contexts, Context availability table]. The workflow-level `env` context is **not** available there, so a shared `env: PLAYER_EVENT` cannot feed the job `if`.
- Today the predicate `github.event_name == 'pull_request'` appears at ci.yml:123 (job `if`) and ci.yml:167 (`PLAYER_REQUESTED`), then is re-branched at :176 and :180.

**Recommendation (smallest change that preserves semantics exactly):** keep the single job-level `if:` as the one definition of "player runs", delete the `PLAYER_REQUESTED` env expression, and in the aggregate script branch on the runner-provided `GITHUB_EVENT_NAME` (not a second YAML expression), with a two-way comment tying it to the job `if`:

```bash
if [[ "$GITHUB_EVENT_NAME" == pull_request ]]; then
  expected_ok='success'
else
  expected_ok='success|skipped'   # job-level `if:` skips it off pull_request
fi
```
Implement as a plain `case "$PLAYER_RESULT" in` to avoid regex quoting. Preserve: PR requires `success`; push accepts `skipped` or `success`; every other value fails closed; messages may change but the job name `required-native` must not.

**Stronger alternative (adds a job; only if the planner wants real single-source):** a tiny `plan` job whose output `player_required=${{ github.event_name == 'pull_request' }}` feeds both the player job `if: needs.plan.outputs.player_required == 'true'` and the aggregate. Costs one runner and one more `needs` edge. Not recommended for an info-level maintainability item.

### Anti-Patterns to Avoid
- **Reading `jobs?filter=all` without checking each job's `run_attempt`:** returns failed jobs from earlier attempts alongside the passing re-run (live example: run 37620710587 lists `cmake-floor-3.25.3` as both `failure` attempt 1 and `success` attempt 2).
- **Treating "status completed + conclusion failure" as final without debounce right after a re-run.**
- **Interpolating the SHA into a jq/shell program** (use argv).
- **Adding a CTest name for the gate self-test** (changes `tests/expected-tests.txt`, which Phases 1, 2, 3, 6 cover, and puts Python on the Windows lane for no gain).

## Common Pitfalls

### Pitfall 1: `action_required` on bot PRs looks like a failure, then flips
**What goes wrong:** the gate fails on `action_required` attempt 1 while a maintainer approval creates attempt 2 on the same run id (observed: run 37863576226).
**Why:** approval re-runs the run rather than creating a new one.
**How to avoid:** D-07's two-poll debounce plus "newest decides" is the only mitigation; accept that a PR whose CI is still awaiting approval fails the gate at the deadline. Self-test must include `action_required` -> fail and "attempt 2 in progress after attempt 1 failed" -> wait.
**Warning signs:** `previous_attempt_url` present in the list entry.

### Pitfall 2: `filter=all` job lists mix attempts
**How to avoid:** use the default `filter=latest`; if a script ever uses `all`, also require `job.run_attempt == run.run_attempt`. Self-test: run with two `required-native` entries (failure attempt 1, success attempt 2) must evaluate on the latest only.

### Pitfall 3: Player artifact name uses the run-level attempt
**What goes wrong:** `phase3-player-candidate-${run_id}-${run_attempt}` is uploaded by `macos-player-package` with `github.run_attempt` of the attempt in which that job executed (ci.yml upload step). The current gate publishes `gh run view --json attempt` (the run's latest attempt). After a "re-run failed jobs" where `macos-player-package` succeeded in attempt 1 and another job failed, attempt 2 carries the player job over `[ASSUMED]`, the run-level attempt is 2, but the artifact is named `...-1` -> `gh run download --name` fails.
**How to avoid:** have the script publish `run_attempt` from the **`macos-player-package` job object** in the latest-jobs response (`job.run_attempt`), with a self-test where run attempt = 2 and the player job's `run_attempt` = 1 asserting output `1`. If the assumption about carried-over jobs is wrong, the value still equals the run attempt in the full re-run case, so the change is safe either way. Flag as a planner decision; hosted evidence for the partial-re-run case is not obtainable without a deliberate re-run.

### Pitfall 4: Gate script now needs a checkout
Reorder steps (checkout first). In the Linux/macOS jobs this means the CI wait begins after checkout, a few seconds later; deadlines still dominate. Keep the exact gate step name/ids that the player job's outputs depend on.

### Pitfall 5: New NULL/0 expectation copied from `test_audio.c`
See "Pitfall" under Audio consumer smoke (budget 8 consumes 0 on the JR program).

### Pitfall 6: Editing a covered `.yml` changes more than one regex-checked contract
`WorkflowOutputDirectoryTests` and `verify-release-candidate.sh` scan workflow text for `GBB_VERIFIED_OUTPUT_DIR` assignments; `verify-pr-evidence.sh` greps `PREVIEW_RETENTION_DAYS:`. Run `python3 -I -m unittest discover -s tests/scripts -p test_verified_player_output_dir.py` after the workflow commit (GB-GSD-010 caller sweep).

### Pitfall 7: Hosted-only verification of the gate
The gate only runs on a real PR; local confidence comes from `--self-test`, `actionlint`, and a dry run against this repo's real history (e.g. `--sha` of a past PR head with `--deadline-seconds 20`), but the authoritative proof is PR 1's own `preview-package-smoke` run on its exact head.

### Pitfall 8: `strict` branch protection and a moving `main`
See Branch protection section; plan a re-merge budget.

### Gate decision core (shape only; planner finalizes names)
```python
# Source: derived from D-07 and the REST semantics verified above
import re
SHA_RE = re.compile(r"^[0-9a-f]{40}$")
BAD = {"failure", "cancelled", "timed_out", "action_required",
       "neutral", "skipped", "stale", "startup_failure"}

def decide(sha, listing, detail, jobs, require, repo_path, state):
    runs = [r for r in listing["workflow_runs"]
            if r["head_sha"] == sha and r["event"] == "pull_request"
            and r["path"] == ".github/workflows/ci.yml"]
    if listing["total_count"] > len(listing["workflow_runs"]):
        return ("FAIL", "run list truncated")
    if not runs:
        return ("WAIT", "no run yet")
    newest = max(runs, key=lambda r: r["run_number"])
    d = detail(newest["id"])
    if any(d.get(k) != newest.get(k) for k in ("run_attempt", "head_sha", "event", "path")):
        return ("WAIT", "list/detail disagree")
    if d["status"] != "completed":
        return ("WAIT", "newest run in progress")
    if d["conclusion"] == "success":
        by_name = {}
        for j in jobs(newest["id"]):   # filter=latest
            by_name.setdefault(j["name"], []).append(j)
        for name in require:
            matches = by_name.get(name, [])
            if len(matches) != 1 or matches[0]["conclusion"] != "success":
                return ("FAIL", "required job missing or not successful: " + name)
        return ("PASS", newest)
    key = (newest["id"], d["run_attempt"])
    state["streak"] = state["streak"] + 1 if state.get("key") == key else 1
    state["key"] = key
    return ("FAIL", d["conclusion"]) if state["streak"] >= 2 else ("WAIT", "debouncing")
```
